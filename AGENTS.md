# Agent Instructions

- When adding or changing UI copy, update only the English and Japanese locale files (`src/locales/en.xml` and `src/locales/ja.xml`) during normal implementation.
- Run the app against the real Tauri/local backend by default. Enable mock data only for validation/test runs by setting `VITE_MOCK_DATA=true`.
- For tasks with a graphics or visual-quality goal, verify against the real Tauri app. Before starting anything, check whether port `1420` or this workspace's `target/debug/musical` is already running. If the existing process is the real Tauri app for this workspace, reuse it and do not start another instance; only run `npm run tauri dev` when no reusable real app exists.
- For every UI addition or modification based on a supplied image, screenshot, mockup, Figma frame, design board, or source capture, use the project `design-qa` skill after implementation and before declaring completion. Treat the supplied visual as the source of truth unless the user explicitly asks for a redesign.
- Run `design-qa` as a strict iteration gate against the real workspace Tauri app: capture fresh implementation evidence at the same viewport, state, theme, device density, and representative content as the reference; compare the reference and implementation together; inspect both the full view and focused regions where details are not clearly readable.
- The implementer must not self-approve image-based UI work. Use a fresh read-only reviewer when subagents are available. Any actionable P0, P1, or P2 visual mismatch blocks completion; fix it, recapture the current build, and repeat independent review until it passes. Do not average away a major mismatch with an overall score, reuse stale screenshots, or call the work complete when comparable visual evidence is unavailable.
- For routine launch, dependency-resolution, or non-visual smoke checks, use the isolated mock Tauri app (`npm run tauri:dev:ai-test`) on port `1430` instead of starting the real app. This test app runs hidden and unfocused in the background, uses mock data and a separate app identifier, never opens the dev browser, and does not start the local server or MCP sidecar on port `1422`.
- Treat the real and AI-test Tauri launchers as mutually exclusive within this workspace. Their ports and app identifiers differ, but both `tauri dev` commands build and run `src-tauri/target/debug/musical` from the same Cargo target directory. Never run `npm run tauri:dev:ai-test` while this workspace's real Tauri dev process is running, and never run `npm run tauri dev` while its AI-test Tauri process is running.
- Before any Tauri launch, inspect all of the following together: listeners on `1420`, `1422`, and `1430`; every `target/debug/musical` process; and the parent commands for matching Vite, Cargo, and Tauri processes. A port listener alone is not proof that the matching Tauri app is running. If ownership or launch mode cannot be established, do not start another instance.
- Do not launch `/Applications/Musical.app`, a built `Musical.app` under `src-tauri/target/**/bundle/`, or any other installed copy to validate the workspace dev app. These copies may share the `Musical` display name or `com.circularmoonray.musical` bundle identifier while containing different versions. The generated wrapper under `src-tauri/target/codex-dev-apps/` is the sole exception: Cargo invokes its executable symlink as part of the normal `tauri dev` process and it must resolve back to this workspace's current `target/debug/musical`.
- When UI automation reports an ambiguous `Musical` app name or bundle identifier, do not resolve the ambiguity by trying candidate app paths: app-state inspection may launch a candidate that is not already running. Continue only when the already-running workspace dev window can be identified without launching another app; otherwise use a non-Tauri validation path or report that visual verification is blocked.
- Treat Computer Use app lookup as an app launch unless proven otherwise. Before the first Computer Use call targeting Musical, snapshot every Musical main process with PID, start time, and executable path, and inspect `lsappinfo` plus the Computer Use app list. Proceed only when exactly one already-running entry has bundle ID `com.circularmoonray.musical.dev` and its executable is the symlink under this workspace's `src-tauri/target/codex-dev-apps/Musical Dev.app` resolving to the current `src-tauri/target/debug/musical`. For the isolated launcher use `com.circularmoonray.musical.ai-test` and apply the same symlink check.
- Never probe the workspace dev app with a bare Computer Use target such as `Musical`, `musical`, or the product ID `com.circularmoonray.musical`. Target only the preflight-verified development ID `com.circularmoonray.musical.dev` (or `com.circularmoonray.musical.ai-test` for the isolated launcher). An absent or mismatched development ID means visual verification is blocked; it is not permission to try a display name, product identifier, or another app path.
- After the first UI-automation call and again after any call that could change app focus or lifecycle, compare the Musical process snapshot with current `ps` and `lsappinfo` output before sending another UI action. If automation launched an extra copy, stop only the newly created exact PID, preserve every pre-existing process, report the incident, and do not continue Computer Use in that task.
- Start at most one Tauri launcher per task. Record its root PID or session when starting it, and terminate only that recorded launcher and its children after verification. Do not use name-wide or bundle-ID-wide termination. If a reused process exits unexpectedly, report it; do not start a replacement merely to restore the appearance of the prior state.
- Stop only the dev process started by the current task after verification. Never stop a reused process owned by another task or the user.
- When changing features, behavior, UI/UX, APIs, data structures, or runtime responsibilities, update the matching specs/docs in the same change set. Use `Specs/feature-list.md` for feature inventory changes, `Specs/basic-design.md` for basic design changes, and the relevant detailed `Specs/*.md` or `docs/*.md` file for behavior-specific changes.
- When preparing a push, read `.codex/push.md` and apply its push-only checklist. For tag pushes, validate every locale file under `src/locales/`, not only English and Japanese.
- Name release tags using `v{major version}.{minor version}.{bugfix version}` (for example, `v1.2.3`).
- Before choosing or changing a release version, fetch Git tags and inspect the tags and release history reachable from the current branch. Base major, minor, or bugfix increments on the latest applicable Git release tag rather than only on version strings in working-tree files.
- Treat an instruction to update the version as authorization to validate and commit the release changes, push the current branch, create the matching `v{major}.{minor}.{bugfix}` tag, and push that tag unless the user explicitly limits the scope.
- Do not satisfy missing locale keys with English fallback text. Missing keys in non-English locale files must be translated, and placeholders such as `{count}` and `{message}` must match the English source.
- Treat `tasklist/` as local-only working notes. Do not stage, commit, or push files under `tasklist/` unless the user explicitly requests that exact path.
